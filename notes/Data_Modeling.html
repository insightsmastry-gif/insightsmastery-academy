2. What Is Data Modeling?

2.1 Simple Meaning

A data model (in Power BI called a semantic model) is the set of tables, relationships, calculations and properties that sits between your raw data and your reports. Every visual sends a query to it. A good model answers those queries correctly, quickly and in business language.

Library Analogy

Raw data is a pile of books on the floor. A data model is the library: shelves (tables), a catalogue (relationships), labels in plain language (names and folders), and a librarian who knows the rules (measures). Readers find what they need without knowing where the books came from.

2.2 Why Not One Big Flat Table?

Beginners often load one wide spreadsheet and build reports directly on it. It works for ten rows — and fails for ten million. The table below compares the two approaches.

ProblemOne flat tableStar schema
Repeated textCustomer, Product, Category repeated on every rowStored once in a small dimension
Model sizeLarge — wide text columns compress poorlySmall — fact table holds narrow numeric keys
Second fact (e.g. targets)Cannot join cleanly; needs another flat table that cannot filter the firstShares the same dimensions; one slicer filters both
Time intelligenceNo proper date tableDedicated date dimension
UsabilityDozens of columns in one listFields grouped by business entity
SecurityRules on a huge tableRules on a small dimension that filter the fact
Microsoft's guidance

Dimension tables enable filtering and grouping; fact tables enable summarization. A well-designed model provides both, and each table should be one or the other — not a mix.

4. Dimensional Modeling Fundamentals

4.1 Fact Tables

A fact table stores events or observations: sales orders, stock balances, exchange rates, website visits. It contains dimension key columns and numeric columns that you summarise. Fact tables are usually long and keep growing.

Fact table typeOne row representsExample
TransactionOne eventOne order line (our FactSales)
Periodic snapshotState at a regular point in timeStock on hand at month end; our monthly FactTarget
Accumulating snapshotOne process with milestone dates that updateOrder → shipped → delivered → paid
Factless factAn event or relationship with no numbersSalesperson covers Region (bridge, Chapter 9)

4.2 Dimension Tables

A dimension table describes the things you model: products, customers, places, people and time. It has one unique key column and descriptive columns used for slicers, rows, columns and filters. Dimensions are usually short and wide.

4.3 Grain — the Most Important Decision

The grain is what one fact row represents. Declare it in one sentence before you build anything: "One row of FactSales is one product on one order."

  • Every fact table must load data at one consistent grain.
  • The dimension keys define the dimensionality; their values define the granularity. FactTarget has Date and Region keys, but its date values are always the first day of a month — so its grain is month × region.
  • Choose the lowest grain the questions need. You can always summarise up; you can never drill below the grain.

4.4 Star Schema vs Snowflake

Figure 4.1 — A star schema: one fact table in the centre, dimension tables around it

Figure 4.2 — A snowflake: the product dimension split into three normalized tables

Microsoft's guidance: generally the benefits of a single denormalized dimension table outweigh a snowflake. A snowflake loads more tables, creates longer filter chains, clutters the Data pane, and prevents a hierarchy that spans tables (Category → Subcategory → Product needs one table).

Rule of thumb

Flatten each business entity into one dimension table in Power Query. Keep separate tables only for different entities.

4.5 Keys

Key typeMeaningExample
Natural (business) keyThe identifier from the source systemProduct name, employee ID
Surrogate keyA unique integer you add for modelingProductKey = 1…6 from a Power Query index column
Foreign keyThe key column in the fact table that points to a dimensionFactSales[ProductKey]

Power BI relationships join on one column. If a dimension has no single unique column, add a surrogate key with Add Column → Index Column, then merge it into the fact query.

Slowly changing — Type 1Attribute overwritten with the latest valueA normal full refresh achieves this

6. Shaping the Tables in Power Query

Power Query turns the flat extract into the star schema before data reaches the model. Doing transformations here — as far upstream as possible — gives better compression and a cleaner model than DAX calculated columns.

6.1 Query Architecture

Figure 6.1 — One staging query feeds every dimension and the fact table

  1. Get data → Text/CSV → Sales.csv → Transform data. Rename the query Sales_Source.
  2. Set data types on every column (Date, Whole number, Fixed decimal number, Text). Do it once, early.
  3. Right-click Sales_Source → Enable load to turn loading off. It is a staging query only.
  4. Right-click Sales_Source → Reference for each dimension, keep only its columns, Remove Duplicates, add an Index Column from 1.
  5. Reference Sales_Source again for FactSales, merge each dimension to bring in its key, then remove the text columns.
  6. Close & Apply.

6.2 DimProduct in M

let
    Source   = Sales_Source,
    Cols     = Table.SelectColumns(Source, {"Product", "Category", "UnitPrice"}),
    Distinct = Table.Distinct(Cols, {"Product"}),
    Sorted   = Table.Sort(Distinct, {{"Product", Order.Ascending}}),
    Keyed    = Table.AddIndexColumn(Sorted, "ProductKey", 1, 1, Int64.Type),
    Ordered  = Table.ReorderColumns(Keyed, {"ProductKey", "Product", "Category", "UnitPrice"})
in
    Ordered

Repeat the same five steps for DimCustomer (Customer, City), DimRegion (Region) and DimSalesperson (Salesperson, Email). Table.Distinct(…, {"Product"}) keeps one row per product even if a price typo appears twice.

6.3 FactSales in M

let
    Source  = Sales_Source,
    MergeP  = Table.NestedJoin(Source, {"Product"}, DimProduct, {"Product"}, "P", JoinKind.LeftOuter),
    ExpP    = Table.ExpandTableColumn(MergeP, "P", {"ProductKey"}),
    MergeC  = Table.NestedJoin(ExpP, {"Customer"}, DimCustomer, {"Customer"}, "C", JoinKind.LeftOuter),
    ExpC    = Table.ExpandTableColumn(MergeC, "C", {"CustomerKey"}),
    MergeR  = Table.NestedJoin(ExpC, {"Region"}, DimRegion, {"Region"}, "R", JoinKind.LeftOuter),
    ExpR    = Table.ExpandTableColumn(MergeR, "R", {"RegionKey"}),
    MergeS  = Table.NestedJoin(ExpR, {"Salesperson"}, DimSalesperson, {"Salesperson"}, "S", JoinKind.LeftOuter),
    ExpS    = Table.ExpandTableColumn(MergeS, "S", {"SalespersonKey"}),
    Keep    = Table.SelectColumns(ExpS, {"SalesID", "OrderDate", "ShipDate", "CustomerKey",
                 "ProductKey", "RegionKey", "SalespersonKey", "Quantity", "SalesAmount", "Cost"})
in
    Keep

Result: FactSales has 10 rows and 10 narrow columns; the six dimension text columns are gone.

6.4 FactTarget in M

let
    Source  = Excel.Workbook(File.Contents("Targets.xlsx"), true){[Item = "Targets"]}[Data],
    Typed   = Table.TransformColumnTypes(Source, {{"Month", type date}, {"Target", Currency.Type}}),
    MergeR  = Table.NestedJoin(Typed, {"Region"}, DimRegion, {"Region"}, "R", JoinKind.LeftOuter),
    ExpR    = Table.ExpandTableColumn(MergeR, "R", {"RegionKey"}),
    Keep    = Table.SelectColumns(ExpR, {"Month", "RegionKey", "Target"})
in
    Keep

Month holds the first day of the month (1-Jan-2026). That date relates to DimDate[Date], but the grain stays month — Chapter 9 explains how to report it safely.

7. The Date Table

A date table is the most common table in any model, and DAX time intelligence needs one. Build it deliberately rather than relying on automatic tables.

7.1 Requirements of a Date Table

  1. A column of data type Date (or Date/Time) — the date column.
  2. Unique values, no BLANKs, no missing dates.
  3. Spans full years (a fiscal year is fine).
  4. Marked as a date table when using classic time intelligence functions.

7.2 Turn Off Auto Date/Time

File → Options and settings → Options → Current File → Data Load → Auto date/time (and the Global setting for new files). Auto date/time creates a hidden date table for every date column, which inflates the model and cannot filter several fact tables with one date slicer.

7.3 Options for Building It

TechniqueWhen to use
Connect to a warehouse date dimensionBest — one organisation-wide definition of time
Generate in Power QueryNo warehouse; you want it computed at refresh
Generate with DAX (CALENDAR / CALENDARAUTO)Quick and fully under your control
Clone with DAX (Ship Date = 'Date')A second role-playing date table (columns only; no formats or hierarchies are copied)

7.4 DimDate with DAX

DimDate =
VAR StartDate = DATE( 2026, 1, 1 )
VAR EndDate   = DATE( 2026, 12, 31 )
RETURN
    ADDCOLUMNS(
        CALENDAR( StartDate, EndDate ),
        "Year",        YEAR( [Date] ),
        "Quarter",     "Q" & QUARTER( [Date] ),
        "Month No",    MONTH( [Date] ),
        "Month",       FORMAT( [Date], "MMM" ),
        "Year Month",  FORMAT( [Date], "YYYY-MM" ),
        "Month Start", DATE( YEAR( [Date] ), MONTH( [Date] ), 1 ),
        "Weekday No",  WEEKDAY( [Date], 2 ),
        "Weekday",     FORMAT( [Date], "ddd" )
    )

Result: 365 rows, 1-Jan-2026 to 31-Dec-2026.

CALENDARAUTO() instead extends the range automatically to full years covering every date in the model, so it grows at each refresh. Use CALENDAR when you want a fixed, explicit range.

7.5 Finish the Table

  1. Select Month → Column tools → Sort by column → Month No (otherwise months sort Apr, Aug, Dec…). Do the same for Weekday → Weekday No.
  2. Hide helper columns (Month No, Weekday No).
  3. Create a hierarchy Calendar: Year → Quarter → Month → Date.
  4. Table tools → Mark as date table → choose the Date column. Power BI validates uniqueness, no blanks and contiguous dates.
  5. Relate DimDate[Date] 1 → * FactSales[OrderDate] (active) and 1 → * FactSales[ShipDate] (inactive).
Calendar-based time intelligence

Microsoft now recommends the newer calendar-based time intelligence (in preview at the time of writing) for the best performance and flexibility with any calendar, including fiscal and retail calendars. Classic functions such as DATESYTD and SAMEPERIODLASTYEAR still work and require a marked date table. Microsoft advises against adding many offset columns to the date table just to simplify DAX.

8. Relationships

Relationships are the filter paths of the model. A visual's filters start on dimension tables and travel along relationships to the fact table, where measures add up the remaining rows.

8.1 Creating Relationships

  1. Model view: drag FactSales[ProductKey] onto DimProduct[ProductKey], or
  2. Modeling → Manage relationships → New: choose both tables and columns.
  3. Check cardinality, cross filter direction and Active in the dialog before selecting OK.

Power BI auto-detects relationships after loading (File → Options → Data Load → Relationships). Always review what it created — automatic guesses can be wrong when data is incomplete.

8.2 Cardinality

TypeMeaningUse
One-to-many (1:*) / Many-to-one (*:1)Unique values on one side, duplicates allowed on the otherAlmost every relationship: dimension → fact
One-to-one (1:1)Unique values on both sidesRare; often a sign two tables should be merged
Many-to-many (*:*)Duplicates allowed on both sidesRelating facts at a higher grain, or cross-source; use deliberately
Refresh failure

If a refresh loads a duplicate value into a column on the "one" side, the entire refresh fails. Guarantee uniqueness in Power Query (Remove Duplicates on the key).

8.3 Cross Filter Direction

Figure 8.1 — A Region filter flows to FactSales, but not onwards to DimProduct (single direction)

CardinalityAllowed directions
One-to-manySingle (from the one side) or Both
One-to-oneBoth
Many-to-manySingle either way, or Both
  • Single — the default and the recommendation for star schemas.
  • Both (bi-directional) — filters also flow from the many side back to the one side. It can hurt performance, can create ambiguous paths, and Power BI may refuse it. Use only for specific patterns such as a many-to-many bridge.
  • Prefer CROSSFILTER(…, BOTH) inside one measure over setting a model relationship to Both.

Example: products sold in the North

A slicer on Region = North does not reduce the Product slicer — all 6 products still appear, because filters do not flow from FactSales to DimProduct. To show only products with North sales, use the slicer's visual filter [Total Sales] is not blank, which is cheaper than making the relationship bi-directional.

8.4 Active and Inactive Relationships

Only one active path may exist between two tables. FactSales has two date columns, so DimDate→OrderDate is active and DimDate→ShipDate is inactive (dashed line). An inactive relationship is used only inside a calculation:

Sales by Ship Date =
CALCULATE(
    [Total Sales],
    USERELATIONSHIP( FactSales[ShipDate], DimDate[Date] )
)
Date range (DimDate)Total Sales (order date)Sales by Ship Date
1–10 Jan 2026276,000236,000
11–12 Jan 2026(blank)40,000

8.5 Regular vs Limited Relationships

RegularLimited
WhenOne-to-many or one-to-one within one source groupMany-to-many cardinality, or a cross-source-group relationship in a composite model
Model view signNormal lineParenthesis-like marks after the cardinality indicators
Join behaviourTable expansion; unmatched fact rows go to a (Blank) memberINNER JOIN; unmatched rows simply disappear

8.6 Referential Integrity and the (Blank) Row

If FactSales contained ProductKey 99 with no matching DimProduct row, a regular relationship would show those sales under (Blank) product. The total stays correct, but users see an unexplained blank. Fix it upstream: add an Unknown member (key −1) to each dimension and map missing keys to it in Power Query.

8.7 Resolving Ambiguity

When bi-directional relationships create several paths, Power BI chooses by priority: paths of one-to-many relationships first, then paths including many-to-many, then many-to-one, and so on; ties are broken by weight, which USERELATIONSHIP can raise. The practical lesson: keep a clean star with single-direction relationships and ambiguity never arises.

FunctionPurposeExample
RELATEDFetch a value from the one side (row context)RELATED(DimProduct[Category])
RELATEDTABLEGet the related rows on the many sideCOUNTROWS(RELATEDTABLE(FactSales))

9. Advanced Relationship Patterns

9.1 Role-Playing Dimensions

One dimension, several meanings. FactSales has OrderDate and ShipDate; both relate to dates. There are two designs.

Figure 9.1 — Design A: one date table, active OrderDate path, inactive ShipDate path

Design A — inactive relationshipDesign B — one table per role
SetupOne DimDate; ShipDate relationship inactiveClone: Ship Date = DimDate, rename its columns (Ship Year, Ship Month…)
Report useOnly through measures with USERELATIONSHIPAny visual can slice by order date and ship date at the same time
MeasuresExtra 'by Ship Date' measuresNo extra measures
Best whenFew role-specific measures; visuals never filter both roles togetherUsers need both roles as slicers, rows or columns

Microsoft generally recommends active relationships where possible, which means duplicating a role-playing dimension (Design B). Use inactive relationships when reports never need to filter by both roles at once.

9.2 Multiple Fact Tables at Different Grains

FactTarget is at month × region; FactSales is at order line. Both relate to the shared dimensions DimDate and DimRegion — these are conformed dimensions, so one slicer filters both facts.

Protecting the month grain

All targets sit on 1-Jan-2026. A visual by day would show 280,000 on 1 January and nothing on other days — misleading. Blank the target below month level:

Total Target =
IF(
    ISINSCOPE( DimDate[Date] ),
    BLANK(),
    SUM( FactTarget[Target] )
)

Microsoft also documents an alternative: relate the higher-grain fact on a month column (e.g. Year Month) with a many-to-many relationship. Whichever you choose, also hide day-level date columns from target-only reports.

9.3 Many-to-Many Dimensions with a Bridge Table

New rule: a salesperson can cover several regions. Priya now covers South and West. Store the coverage in a bridge (factless fact) table:

Not additive — and that is correct

The rows add to 330,000 but the total shows 280,000. West's 50,000 target is shared by Priya and Amit, and the total counts it once. Many-to-many measures are non-additive; explain this to report users.

One-to-oneUsually merge the two tables in Power Query. Keep separate only when they come from different sources or one is optional.

10.1 Where Should a Calculation Live?

Rule

Shape data as far upstream as possible, and as far downstream as necessary. Columns go upstream (Power Query or the source); aggregations become measures.

10.2 The Core Measures

Total Sales       = SUM( FactSales[SalesAmount] )

10.3 Organising Measures

  • Explicit measures only — hide numeric fact columns so users cannot drag them in and get implicit sums. Turn on Discourage implicit measures in the model properties.
  • Measure table — Home → Enter data, one column, name it _Measures; move measures there (set each measure's Home table); hide the column. It appears at the top of the Data pane.
  • Display folders — Model view → Properties → Display folder, e.g. Sales, Profit, Targets. Use \ for subfolders.
  • Format strings — set once on the measure (#,##0; 0.00%). Dynamic format strings can change format by context.
  • Descriptions — fill in every measure's description; it shows as a tooltip in the Data pane and helps Copilot and Q&A.

10.4 Calculation Groups

A calculation group applies one expression pattern to any measure, replacing dozens of near-duplicate measures. Create it in Model view (Calculation group on the ribbon) or in TMDL view. SELECTEDMEASURE() is the placeholder for whichever measure is in the visual.

Calculation group: Time Calc   (column: Time Calc)

  Current = SELECTEDMEASURE()
  MTD     = CALCULATE( SELECTEDMEASURE(), DATESMTD( DimDate[Date] ) )
  YTD     = CALCULATE( SELECTEDMEASURE(), DATESYTD( DimDate[Date] ) )
  PY      = CALCULATE( SELECTEDMEASURE(), SAMEPERIODLASTYEAR( DimDate[Date] ) )

Put Time Calc on the columns of a matrix with Total Sales and Total Profit in values: four versions of each measure without writing eight measures. On 10 Jan 2026, YTD Sales = 276,000 and PY = blank (no 2025 data). Creating a calculation group turns on Discourage implicit measures automatically. When several calculation groups apply, precedence decides the order.

10.5 Field Parameters

Modeling → New parameter → Fields creates a table that lets users switch which measure or column a visual uses (Sales / Profit / Quantity; Region / Category). It is a model object, so plan its name and place like any table.

12. Storage Modes and Composite Models

12.1 The Storage Modes

ModeWhere data livesStrengthsWatch out
ImportCompressed in memory (VertiPaq)Fastest queries; full DAX and Power QueryData is as fresh as the last refresh; model size limits
DirectQueryStays in the source; queried liveNear real-time; very large dataSlower; source must be tuned; 1,000,000-row intermediate result limit; some modeling limits
DualBoth imported and DirectQueryDimensions answer slicers from memory and join natively to DirectQuery factsNeeds refresh like Import
Direct Lake (Fabric)Delta tables in OneLake, loaded on demandImport-like speed without copying dataFabric capacity; specific limitations
Hybrid tableImport partitions + one DirectQuery partitionFast history plus live recent dataSet up via incremental refresh; no aggregations on hybrid tables
Default choice

Start with Import. Move to DirectQuery, Dual or Direct Lake only for a specific reason: data volume, freshness, or a governed Fabric lakehouse.

12.2 Composite Models

A composite model mixes storage modes or sources. Recommended pattern: large fact tables in DirectQuery, their dimensions in Dual, small reference tables in Import.

Figure 12.1 — Relationships inside one source group are regular; cross-source relationships are limited

  • Relationships across source groups are created as many-to-many and are always limited: INNER JOIN behaviour, no RELATED, possible performance cost.
  • Use Dual for dimensions queried with DirectQuery facts from the same source — it avoids limited relationships.
  • Strive for data integrity across sources: limited relationships drop rows whose keys do not match.
  • Direct Lake + Import composite models (Fabric web modeling) support regular relationships.

12.3 User-Defined Aggregations

An aggregation table (for example sales by Month × Category, imported) answers high-level visuals from memory while detailed visuals still hit the DirectQuery fact. Microsoft's rule of thumb: the aggregation should have at least 10× fewer rows than the table it summarises.

12.4 Choosing a Mode

SituationChoose
Up to tens of millions of rows; daily refresh is fineImport
Billions of rows or minute-level freshness from a tuned warehouseDirectQuery facts + Dual dimensions (+ aggregations)
Data already in a Fabric lakehouse or warehouseDirect Lake
Years of history plus today's transactionsHybrid table via incremental refresh with real-time data
Extend a published semantic model with your own Excel targetsComposite model (DirectQuery to the semantic model + Import)

13. Row-Level Security

Row-level security (RLS) restricts which rows each viewer sees. Roles hold DAX filter rules; each rule is evaluated per row and the row is visible when it returns TRUE.

13.1 Static RLS

  1. Modeling → Manage roles → New; name the role North Team.
  2. Select table DimRegion; rule [Region] = "North".
  3. Save. Modeling → View as → North Team to test.

Result: Total Sales = 131,000 for every visual.

13.2 Dynamic RLS

One role filters differently for every user by comparing an email column with the signed-in identity.

13.3 Publishing and Role Mapping

  • Users are assigned to roles in the Power BI service (semantic model → Security), not in Desktop.
  • Map roles to security groups rather than individuals.
  • RLS applies to workspace Viewers. Admins, Members and Contributors can edit the model, so RLS does not apply to them.
  • Test in the service with Test as role; for dynamic RLS and B2B guests, sign in as the real user to be sure.

13.4 RLS Best Practices

  • Put rules on dimension tables, not fact tables, and let relationships propagate them.
  • RLS propagates only through active relationships.
  • Avoid LOOKUPVALUE in rules when a relationship can do the job.
  • Write rules so unexpected values return no rows, never all rows.
  • Measure the cost with Performance Analyzer: compare visual durations with and without View as.
Safe rule pattern (Microsoft)

A rule like IF(USERNAME() = "Worker", [Type] = "Internal", TRUE()) shows everything to a mistyped value. Test each expected value explicitly and end with FALSE():
IF(USERNAME()="Worker", [Type]="Internal", IF(USERNAME()="Manager", TRUE(), FALSE()))

14. Performance and Size Optimization

14.1 How VertiPaq Stores Data

Import models are stored column by column and compressed — roughly 10× compression in memory is typical. Each column is encoded separately:

  • Value encoding for numbers — very efficient.
  • Hash (dictionary) encoding for text and other non-numeric data — each distinct value gets an ID, so size grows with the number of distinct values.
  • Therefore column cardinality (number of distinct values) is the main driver of model size, more than row count.
