3. DAX Foundations in Brief

3.1 What is DAX?

DAX stands for Data Analysis Expressions. It is the formula language of Power BI, Excel Power Pivot and Analysis Services (SSAS Tabular and Azure). DAX is not a programming language like Python — it is a calculation language designed for business intelligence.

Simple Analogy

In Excel you write =SUM(A1:A10). In Power BI you write similar ideas, but DAX understands tables, relationships and filters automatically.

3.2 Measures vs Calculated Columns

AspectCalculated ColumnMeasure
When calculatedAt data refresh, for every rowAt query time, based on filters
ContextRow contextFilter context
StorageStored in the model (uses memory)Not stored; calculated on demand
Typical useNew attributes, flags, per-row valuesTotals, averages, percentages, KPIs
ExampleProfit = Sales[SalesAmount] - Sales[Cost]Total Sales = SUM(Sales[SalesAmount])
Teacher Tip

If the number must change when the user clicks a slicer → use a Measure. If it is a fixed attribute of each row → a Calculated Column is often fine.

3.3 Filter Context

Filter context means "the filters currently affecting your calculation." It comes from slicers, page and visual filters, the rows and columns of a matrix, cross-filtering, relationships, and filters written inside CALCULATE.

Total Sales =
SUM(Sales[SalesAmount])

With no filters this returns 276,000. Put Region on the rows of a matrix and the same measure returns North 131,000, South 105,000, West 40,000. You never write three measures — one measure plus the visual's filter context does the work.

Window Analogy

Filter context is a window. You only see the rows the current filters allow. Change a slicer and the window changes — measures recalculate automatically.

3.4 Row Context

Row context means Power BI knows which single row it is looking at. It exists in calculated columns (always) and inside iterator functions: SUMX, COUNTX, AVERAGEX, FILTER, RANKX and others.

Key Distinction

Row context = "I am looking at one specific row right now."
Filter context = "These are the rows currently visible because of filters."
They are different. CALCULATE can turn a row context into a filter context — this is context transition (Chapter 6, Version 16).

4. SUMX — Deep Dive

This is one of the most important functions in DAX. SUM adds an existing column. SUMX calculates something for every row and then adds the results.

4.1 SUMX Step by Step

1. What is it?

SUMX is an iterator. It walks through a table one row at a time, evaluates an expression on each row, then returns the sum of those results.

2. Why do we need it?

SUM accepts only a single column. The moment you need Quantity × Price, SalesAmount − Cost, a discount, or IF logic per row, you need SUMX.

3. Syntax

SUMX(
    <table>,
    <expression>
)

4. Every word

PartMeaning
SUMXThe function name. The X means it iterates (goes row by row).
<table>The rows to walk through. Can be a table name, FILTER(…), VALUES(…) or ALL(…).
<expression>What to calculate on each row. It is evaluated in row context.
Return valueThe sum of all non-blank results.

5. How SUMX works internally

Take the table (after current filters)
      ↓
Row 1 → evaluate expression → keep result
Row 2 → evaluate expression → keep result
  …   (every visible row)
      ↓
Add all the kept results
      ↓
Return the total
When to choose SUM vs SUMX

• Use SUM when you only need to add an existing numeric column.
• Use SUMX when you need to calculate an expression (multiply, subtract, IF logic, etc.) for each row, or total only certain rows.

4.2 Pattern 1 — SUMX over one column (same as SUM)

Total Sales SUMX =
SUMX(
    Sales,
    Sales[SalesAmount]
)

Result = 276,000

The result is identical to SUM(Sales[SalesAmount]). It works, but SUM is simpler — prefer SUM here. This pattern exists to teach the shape of SUMX.

4.3 Pattern 2 — Quantity × Unit Price

Revenue =
SUMX(
    Sales,
    Sales[Quantity] * Sales[UnitPrice]
)

Read it like English:

«Go through every row of Sales. For each row multiply Quantity by UnitPrice. Then add all those results together.»

RowQuantityUnitPriceCalculationRow result
1250,0002 × 50,000100,000
251,0005 × 1,0005,000
332,0003 × 2,0006,000
9101,00010 × 1,00010,000
……………
Sum of all 10 rows276,000

Result = 276,000

Why can't we write SUM(Sales[Quantity] * Sales[UnitPrice])? Because SUM only accepts a column, not an expression. SUMX exists exactly for this reason. Note: SUM(Sales[Quantity]) * SUM(Sales[UnitPrice]) gives 32 × 159,000 = 5,088,000 — completely wrong. Multiply first, then add.

4.4 Pattern 3 — Row-level subtraction (Profit)

Total Profit X =
SUMX(
    Sales,
    Sales[SalesAmount] - Sales[Cost]
)

Result = 70,500

No Profit column needed: the subtraction happens row by row inside the iterator, so the model does not have to store an extra calculated column.

4.5 Pattern 4 — SUMX with FILTER, one condition

North Sales X =
SUMX(
    FILTER( Sales, Sales[Region] = "North" ),
    Sales[SalesAmount]
)

Read it like English:

«First keep only the North rows. Then walk through those rows and add SalesAmount.»

Result = 131,000 (rows 1, 3, 6, 9 → 100,000 + 6,000 + 15,000 + 10,000)

4.6 Pattern 5 — SUMX with FILTER, AND (&&)

North Electronics X =
SUMX(
    FILTER(
        Sales,
        Sales[Region] = "North"
            && Sales[Category] = "Electronics"
    ),
    Sales[SalesAmount]
)

Result = 116,000 (rows 1, 3, 9)

4.7 Pattern 6 — SUMX with FILTER, OR (||) and IN

North or Furniture X =
SUMX(
    FILTER(
        Sales,
        Sales[Region] = "North"
            || Sales[Category] = "Furniture"
    ),
    Sales[SalesAmount]
)

Result = 191,000 (North rows 1, 3, 6, 9 plus Furniture rows 5, 8, 10)

Laptop or Desk X =
SUMX(
    FILTER( Sales, Sales[Product] IN { "Laptop", "Desk" } ),
    Sales[SalesAmount]
)

Result = 195,000 (Laptop 150,000 + Desk 45,000)

4.8 Pattern 7 — IF logic inside the expression (commission)

Business rule: salespeople earn 5% commission on orders above 30,000 and 2% on everything else.

Commission =
SUMX(
    Sales,
    IF(
        Sales[SalesAmount] > 30000,
        Sales[SalesAmount] * 0.05,
        Sales[SalesAmount] * 0.02
    )
)
GroupRowsSalesRateCommission
Above 30,0001, 7150,0005%7,500
30,000 or belowthe other 8126,0002%2,520
Total276,00010,020

Result = 10,020

A single rate on the total (276,000 × 5%) would give 13,800 — wrong. The rate must be decided per row, which is exactly what SUMX does.

4.9 Pattern 8 — Tax, discount and constants

Sales incl. GST =
SUMX(
    Sales,
    Sales[SalesAmount] * 1.18
)

Result = 325,680

For a flat rate this equals SUM(Sales[SalesAmount]) * 1.18. SUMX becomes essential when the rate differs by row — for example a GST rate stored in a column.

4.10 Pattern 9 — SUMX over VALUES (context transition)

SUMX can iterate a list of unique values instead of the fact table. When a measure is used inside, each value becomes a filter (context transition).

Sales from Big Customers =
SUMX(
    VALUES( Sales[Customer] ),
    IF( [Total Sales] > 50000, [Total Sales] )
)

Read it like English:

«Take the list of customers. For each customer, calculate that customer's Total Sales. If it is above 50,000, keep it. Add what you kept.»

Customer[Total Sales] for that customer> 50,000?Kept
Amit140,000Yes140,000
Neha55,000Yes55,000
Priya50,000No—
Rahul31,000No—
Total195,000

Result = 195,000

Why this works

Inside SUMX there is a row context on each customer. [Total Sales] is a measure, and every measure is wrapped in an invisible CALCULATE. That CALCULATE turns the current customer into a filter, so [Total Sales] returns only that customer's sales. Without a measure (plain SUM) this would not happen.

4.11 Pattern 10 — SUMX inside CALCULATE

North Revenue =
CALCULATE(
    SUMX( Sales, Sales[Quantity] * Sales[UnitPrice] ),
    Sales[Region] = "North"
)
CALCULATE
   ↓  changes filter context to North
   ↓  only North rows remain
SUMX iterates those North rows
   ↓  Quantity × UnitPrice per row
   ↓  sums the results

Result = 131,000

4.12 Related iterators: AVERAGEX, MAXX, MINX, RANKX

AVERAGEX — average of ratios vs ratio of totals

Avg Row Margin % =
AVERAGEX(
    Sales,
    DIVIDE( Sales[Profit], Sales[SalesAmount] )
)

Result = 31.50%

Overall Margin % =
DIVIDE(
    SUM( Sales[Profit] ),
    SUM( Sales[SalesAmount] )
)

Result = 25.54%

Which margin is correct?

Both are correct answers to different questions. AVERAGEX gives every order equal weight, so small orders with high margins (Mouse, Keyboard) pull the average up. The ratio of totals weights by money. Finance teams almost always want the ratio of totals.

MAXX and MINX

Biggest Order = MAXX( Sales, Sales[SalesAmount] )          -- 100,000
Best Customer Sales = MAXX( VALUES(Sales[Customer]), [Total Sales] )  -- 140,000

RANKX — rank customers by sales

Customer Rank =
RANKX(
    ALL( Sales[Customer] ),
    [Total Sales],
    ,
    DESC
)
CustomerTotal SalesCustomer Rank
Amit140,0001
Neha55,0002
Priya50,0003
Rahul31,0004

ALL(Sales[Customer]) gives the full list to rank against, ignoring the current row's filter. DESC puts the highest value at rank 1.

5. COUNTX — Deep Dive

Functions ending with X iterate a table row by row. COUNTX counts how many rows give a non-blank result for an expression — which makes it the tool for conditional counting.

5.1 COUNTX Step by Step

Syntax

COUNTX(
    <table>,
    <expression>
)
PartMeaning
<table>The rows to walk through: a table, FILTER(…), VALUES(…).
<expression>Evaluated on each row. Rows where it returns BLANK are not counted.
Return valueThe number of rows with a non-blank result.
The golden rule of COUNTX

COUNTX counts non-blank results. To skip a row, make the expression return BLANK — usually with an IF that has no 'else' part.

5.2 Pattern 1 — Basic COUNTX

Order Count X =
COUNTX(
    Sales,
    Sales[SalesID]
)

Result = 10

5.3 Pattern 2 — Conditional count with IF

High Value Orders =
COUNTX(
    Sales,
    IF( Sales[SalesAmount] > 30000, Sales[SalesID] )
)
  1. Row 1: 100,000 > 30,000? Yes → return SalesID → counted.
  2. Row 2: 5,000 > 30,000? No → IF returns BLANK → not counted.
  3. Row 4: 30,000 > 30,000? No (equal is not greater) → not counted.
  4. Row 7: 50,000 > 30,000? Yes → counted.
  5. Continue to the last row and return the count.

Result = 2 (rows 1 and 7)

Change > to >= and the result becomes 4 (rows 1, 4, 7, 10). Boundaries matter.

5.4 Pattern 3 — COUNTX with FILTER

North Orders X =
COUNTX(
    FILTER( Sales, Sales[Region] = "North" ),
    Sales[SalesID]
)

Result = 4

5.5 Pattern 4 — Multiple conditions

Bulk Electronics Orders =
COUNTX(
    FILTER(
        Sales,
        Sales[Category] = "Electronics"
            && Sales[Quantity] >= 3
    ),
    Sales[SalesID]
)

Result = 3 (rows 2, 3, 9 — Mouse × 5, Keyboard × 3, Mouse × 10)

5.6 Pattern 5 — Count rows meeting a calculated test

Orders with Profit ≥ 5000 =
COUNTX(
    Sales,
    IF( Sales[SalesAmount] - Sales[Cost] >= 5000, 1 )
)

Result = 6 (rows 1, 4, 5, 6, 7, 10)

5.7 Pattern 6 — Count customers, not rows (with a measure)

Big Customers =
COUNTX(
    VALUES( Sales[Customer] ),
    IF( [Total Sales] > 50000, 1 )
)

Result = 2 (Amit 140,000 and Neha 55,000)

Iterating VALUES(Sales[Customer]) counts customers. Iterating Sales would count orders. Always ask: what am I counting?

5.8 COUNTX vs COUNTROWS vs DISTINCTCOUNT

FormulaCountsResult
COUNTROWS(Sales)Every visible row10
COUNTROWS(FILTER(Sales, Sales[Region]="North"))Rows passing the test4
COUNTX(Sales, Sales[SalesID])Rows where SalesID is not blank10
DISTINCTCOUNT(Sales[Customer])Unique customers4
COUNTROWS(VALUES(Sales[Region]))Unique regions visible3
Which one should I use?

• Counting rows with a condition → COUNTROWS(FILTER(…)) or CALCULATE(COUNTROWS(Sales), filter) — clearest.
• Counting non-blank results of a calculation → COUNTX.
• Counting unique things → DISTINCTCOUNT.
COUNTX and COUNTROWS differ only when the expression can be blank: if SalesID were blank on one row, COUNTX would return 9 and COUNTROWS 10.

5.9 CALCULATE + COUNT family

North Order Count =
CALCULATE(
    COUNTROWS( Sales ),
    Sales[Region] = "North"
)

Result = 4

North Customers =
CALCULATE(
    DISTINCTCOUNT( Sales[Customer] ),
    Sales[Region] = "North"
)

Result = 2 (Amit and Rahul)

6. CALCULATE — The Heart of DAX

If you master CALCULATE, you master DAX. This chapter explains exactly how it works, then walks through 20 versions of CALCULATE — every filter pattern you will meet in real reports.

6.1 What CALCULATE Does

1. What is it?

CALCULATE evaluates an expression in a modified filter context. You give it something to calculate, and a list of filters to add, replace or remove first.

2. Syntax

CALCULATE(
    <expression>,
    <filter1>,
    <filter2>,
    …
)
PartMeaning
<expression>Always first. Any scalar calculation: a measure, SUM, COUNTROWS, SUMX, AVERAGEX…
<filter>Zero or more. A Boolean condition, a table expression (FILTER, VALUES, ALL…), or a filter modifier (REMOVEFILTERS, KEEPFILTERS, USERELATIONSHIP, CROSSFILTER).
Several filtersCombined with AND — every filter must be satisfied.

3. The order CALCULATE follows

  1. Evaluate the filter arguments in the original filter context.
  2. Context transition — if there is a row context, turn the current row into filters.
  3. Apply modifiers — ALL / REMOVEFILTERS / USERELATIONSHIP / CROSSFILTER.
  4. Apply the filter arguments — a filter on a column replaces any existing filter on that same column (unless wrapped in KEEPFILTERS, which intersects instead).
  5. Evaluate the expression in the new filter context and return the result.
The two rules to remember

Rule 1 — Replace: a CALCULATE filter on Region replaces any Region filter coming from a slicer or matrix row. Filters on other columns stay untouched.
Rule 2 — AND: several filter arguments work together; all must be true.

6.2 Version 1 — One Boolean filter

North Sales =
CALCULATE(
    [Total Sales],
    Sales[Region] = "North"
)

Read it like English:

«Calculate Total Sales, but only for the rows where Region is North.»

Result = 131,000

More of the same shape: Sales[Category] = "Electronics" → 201,000 · Sales[Salesperson] = "Ravi" → 131,000 · Sales[Region] = "South" → 105,000.

6.3 Version 2 — Multiple filters (AND)

North Electronics Sales =
CALCULATE(
    [Total Sales],
    Sales[Region] = "North",
    Sales[Category] = "Electronics"
)

Result = 116,000

Each comma is an AND. Writing Sales[Region] = "North" && Sales[Category] = "Electronics" as one argument gives the same result.

6.4 Version 3 — OR on the same column (|| and IN)

North or South Sales =
CALCULATE(
    [Total Sales],
    Sales[Region] = "North" || Sales[Region] = "South"
)
North or South Sales (IN) =
CALCULATE(
    [Total Sales],
    Sales[Region] IN { "North", "South" }
)

Result = 236,000 (131,000 + 105,000)

IN { … } is cleaner once you have three or more values. The opposite, NOT Sales[Region] IN { "West" }, also returns 236,000.

6.5 Version 4 — OR across different columns

You cannot use commas for OR — commas mean AND. For OR across two columns, filter a table that holds both columns:

North or Furniture Sales =
CALCULATE(
    [Total Sales],
    FILTER(
        ALL( Sales[Region], Sales[Category] ),
        Sales[Region] = "North" || Sales[Category] = "Furniture"
    )
)

Result = 191,000

ALL(Sales[Region], Sales[Category]) builds the list of every Region–Category combination; FILTER keeps the combinations that satisfy the OR. In current Power BI versions a Boolean filter may reference several columns of the same table, so Sales[Region] = "North" || Sales[Category] = "Furniture" written directly also works.

6.6 Version 5 — Numeric comparisons

High Value Sales =
CALCULATE(
    [Total Sales],
    Sales[SalesAmount] > 30000
)

Result = 150,000 (rows 1 and 7)

Mid-range Sales =
CALCULATE(
    [Total Sales],
    Sales[SalesAmount] >= 10000 && Sales[SalesAmount] <= 30000
)

Result = 115,000 (rows 4, 5, 6, 8, 9, 10)

6.7 Version 6 — Date filters

Sales Before 6 Jan =
CALCULATE(
    [Total Sales],
    Sales[Date] < DATE( 2026, 1, 6 )
)

Result = 161,000 (rows 1–5)

Sales 3–7 Jan =
CALCULATE(
    [Total Sales],
    Sales[Date] >= DATE( 2026, 1, 3 ) && Sales[Date] <= DATE( 2026, 1, 7 )
)

Result = 121,000 (rows 3–7)

Common mistake

Sales[Date] < "2026-01-06" compares a date with text. Always build dates with DATE(year, month, day).

6.8 Version 7 — Boolean filter vs FILTER(Table) vs FILTER(ALL(Column))

These three look alike but behave differently inside a visual. A Boolean filter is shorthand for FILTER(ALL(column), condition), so it replaces the existing filter on that column. FILTER(Sales, …) iterates only the rows already visible, so it keeps the existing filter.

A  Boolean      = CALCULATE( [Total Sales], Sales[Region] = "North" )
B  FILTER(ALL)  = CALCULATE( [Total Sales],
                     FILTER( ALL( Sales[Region] ), Sales[Region] = "North" ) )
C  FILTER(table)= CALCULATE( [Total Sales],
                     FILTER( Sales, Sales[Region] = "North" ) )

Put Region on the rows of a matrix and add all three:

Matrix rowA BooleanB FILTER(ALL)C FILTER(Sales)
North131,000131,000131,000
South131,000131,000(blank)
West131,000131,000(blank)
Total131,000131,000131,000
Best practice

Prefer Boolean filters on columns (A). They are clearer and faster. Use FILTER(Sales, …) only when you need a condition the Boolean form cannot express — and avoid filtering an entire large table when filtering one column is enough.

6.9 Version 8 — Filtering by a measure

A Boolean filter cannot contain a measure. CALCULATE([Total Sales], [Total Sales] > 50000) returns an error. Iterate a list with FILTER instead:

Sales from Big Customers =
CALCULATE(
    [Total Sales],
    FILTER(
        VALUES( Sales[Customer] ),
        [Total Sales] > 50000
    )
)

Result = 195,000 (Amit 140,000 + Neha 55,000)

FILTER walks the customer list; for each customer [Total Sales] is evaluated (context transition); only Amit and Neha pass; CALCULATE then totals their sales.

6.13 Version 12 — KEEPFILTERS — intersect instead of replace

Without KEEPFILTERS, the North filter replaces the South row filter. With KEEPFILTERS, both filters apply: South AND North has no rows, so the result is blank. Use it when a measure must respect what the user is looking at.

6.14 Version 13 — Nested CALCULATE — the inner filter wins

Inner Wins =
CALCULATE(
    CALCULATE( [Total Sales], Sales[Region] = "South" ),
    Sales[Region] = "North"
)

Result = 105,000 (South)

The outer CALCULATE sets Region = North, then the inner CALCULATE replaces it with South. Wrap the inner filter in KEEPFILTERS and the result becomes blank (North AND South).

6.15 Version 14 — Overriding one filter while keeping others

Electronics Sales (any category slicer) =
CALCULATE(
    [Total Sales],
    Sales[Category] = "Electronics"
)

With a slicer set to Region = South and Category = Furniture, this measure returns 55,000: the Category slicer is replaced by Electronics, but the Region = South filter is kept (rows 2 and 7).

Think in columns

CALCULATE only touches the columns named in its filters. Everything else from the report stays in place.

6.16 Version 15 — CALCULATE with iterators

North Average Profit =

6.17 Version 16 — CALCULATE with no filters — context transition

In a calculated column there is a row context but no filter context. SUM ignores the row; CALCULATE turns the row into a filter.

Col A = SUM( Sales[SalesAmount] )
Col B = CALCULATE( SUM( Sales[SalesAmount] ) )
Col C = CALCULATE( SUM( Sales[SalesAmount] ),
                  ALLEXCEPT( Sales, Sales[Customer] ) )
RowCustomerSalesAmountCol ACol BCol C
1Amit100,000276,000100,000140,000
2Neha5,000276,0005,00055,000
4Amit30,000276,00030,000140,000
7Neha50,000276,00050,00055,000
  • Col A — no context transition: every row sees the whole table.
  • Col B — context transition: the current row becomes a filter, so the row sees only itself.
  • Col C — context transition, then ALLEXCEPT keeps only the Customer filter: each row shows its customer's total.
ROW CONTEXT → CALCULATE (or a measure call) → CONTEXT TRANSITION → FILTER CONTEXT → EVALUATION
Remember

Calling a measure inside an iterator or a calculated column triggers context transition automatically, because every measure is wrapped in an invisible CALCULATE.

6.18 Version 17 — Variables with CALCULATE

Profit Margin % =
VAR TotalSales  = [Total Sales]
VAR TotalProfit = CALCULATE( SUM( Sales[Profit] ) )
RETURN
    DIVIDE( TotalProfit, TotalSales )

Result = 25.54%

North Share % =
VAR NorthSales = CALCULATE( [Total Sales], Sales[Region] = "North" )
VAR AllSales   = CALCULATE( [Total Sales], REMOVEFILTERS( Sales ) )
RETURN
    DIVIDE( NorthSales, AllSales )

Result = 47.46%

Variables are evaluated once, where they are defined. They make long CALCULATE formulas readable and easy to debug — return one variable at a time to test it.

MAX(Sales[Date]) is read in the original context (the matrix row), then ALL removes the date filter and FILTER keeps every date up to that one.

With a marked Date table, time-intelligence functions are shortcuts for the same idea: CALCULATE([Total Sales], DATESYTD('Date'[Date])) for year-to-date and CALCULATE([Total Sales], SAMEPERIODLASTYEAR('Date'[Date])) for last year.

6.20 Version 19 — USERELATIONSHIP and CROSSFILTER

These modifiers change how relationships behave, so they need a model with more than one table. Suppose Sales has OrderDate (active relationship to 'Date') and ShipDate (inactive relationship).

Sales by Ship Date =
CALCULATE(
    [Total Sales],
    USERELATIONSHIP( Sales[ShipDate], 'Date'[Date] )
)

USERELATIONSHIP switches on the inactive relationship for this calculation only; the active one is switched off meanwhile.

Customers Who Bought =
CALCULATE(
    DISTINCTCOUNT( Customer[CustomerID] ),
    CROSSFILTER( Sales[CustomerID], Customer[CustomerID], BOTH )
)

CROSSFILTER changes the filter direction for one calculation (Both, OneWay, or None to disable the relationship) — safer than setting the whole model to bidirectional.

6.21 Version 20 — CALCULATETABLE — the table version

CALCULATETABLE does exactly what CALCULATE does, but returns a table instead of a single value.

North Customer Count =
COUNTROWS(
    CALCULATETABLE(
        VALUES( Sales[Customer] ),
        Sales[Region] = "North"
    )
)

Result = 2 (Amit, Rahul)

7. Classroom Notes — Class of 29 September 2026

This chapter records the five measures written in class, in order. They use a Shop table (a coffee-shop sales log) with the columns OrderDate, Product, PaymentMethod and SalesAmount. The class moved from a plain SUM, to conditional totals with SUMX + FILTER, to CALCULATE for stacking several filters.

7.1 Syntax covered in class

FunctionSyntaxOrder of arguments
CALCULATECALCULATE(Expression, Filter1, Filter2, …)Expression first
SUMXSUMX(Table, Expression)Table first
COUNTXCOUNTX(Table, Expression)Table first
AVERAGEXAVERAGEX(Table, Expression)Table first
RANKXRANKX(Table, Expression)Table first

The table argument of any X function can itself be FILTER(…). That is how you get a conditional total.

7.2 DAX 1 — SUM

Dax1 =
-- SUM('Table'[Column Name])
SUM( 'Shop'[SalesAmount] )

A plain total of one column, with no conditions of its own. Slicers and visuals do all the filtering.

7.3 DAX 2 — SUMX

Dax2 =
-- SUMX(Table, Expression) — the table can be narrowed with FILTER
SUMX( 'Shop', 'Shop'[SalesAmount] )

Same result as DAX 1, because the expression is a single column. SUMX earns its keep when the expression is a calculation or the table is filtered.

7.4 DAX 3 — SUMX + FILTER, one condition

Dax2_1_Cash =
SUMX(
    FILTER( Shop, Shop[PaymentMethod] = "Cash" ),
    'Shop'[SalesAmount]
)

FILTER keeps only Cash rows; SUMX adds SalesAmount for those rows.

7.5 DAX 4 — SUMX + FILTER, two conditions

Dax2_1_Cash_Product =
SUMX(
    FILTER(
        Shop,
        Shop[PaymentMethod] = "Cash"
            && Shop[Product] = "Latte"
    ),
    'Shop'[SalesAmount]
)

&& means AND: a row must be both Cash and Latte.

7.6 DAX 5 — CALCULATE with a date filter

Dax2_1_2_Cash_Product =
CALCULATE(
    SUMX(
        FILTER(
            Shop,
            Shop[PaymentMethod] = "Cash"
                && Shop[Product] = "Latte"
        ),
        'Shop'[SalesAmount]
    ),
    FILTER( Shop, Shop[OrderDate] < DATE( 2024, 4, 1 ) )
)
  1. CALCULATE first applies its filter: only orders dated before 1 April 2024.
  2. Inside that context, SUMX + FILTER keeps the Cash and Latte rows.
  3. SUMX adds SalesAmount for what remains: Cash, Latte, before April 2024.

Recommended rewrite

Cash Latte Sales Before Apr 2024 =
CALCULATE(
    SUM( Shop[SalesAmount] ),
    Shop[PaymentMethod] = "Cash",
    Shop[Product] = "Latte",
    Shop[OrderDate] < DATE( 2024, 4, 1 )
)

Same number, easier to read, faster to run. Column filters touch one column each; FILTER(Shop, …) scans the whole table row by row.

8.2 DAX Debugging Process

  1. Check the table — does it exist and contain the expected rows?
  2. Check the column — spelled correctly? Right data type? Numbers stored as text cause problems.
  3. Check filter context — which slicers, page filters and visual filters are active?
  4. Check row context — are you inside an iterator or a calculated column?
  5. Test the base measure — does the simplest version (e.g. SUM) return the right number?
  6. Test FILTER separately — a temporary measure returning COUNTROWS(FILTER(…)) shows how many rows pass.
  7. Build CALCULATE one filter at a time — add a filter, check, add the next.
  8. Use variables — RETURN each VAR in turn to see its value.
Pro Tip

Create temporary measures named Test1, Test2 while debugging and compare them against the green results in this handbook. Delete them once the final measure works.
